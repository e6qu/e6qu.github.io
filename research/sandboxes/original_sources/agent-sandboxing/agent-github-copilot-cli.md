## Summary
GitHub Copilot CLI (`copilot`) is a local terminal agent that runs as the user. By default it is gated only by tool-level controls: a trusted-directory prompt, per-tool approvals, heuristic path and URL checks, and `--allow-tool`/`--deny-tool` rules. It also has a first-party **local sandbox**, which is **off by default** and is turned on with `/sandbox enable` (persisted as `sandbox.enabled`) or per session with `--sandbox`. The sandbox is built on Microsoft eXecution Container (MXC): Seatbelt on macOS, bubblewrap on Linux, and native sandboxing on recent Windows 11 builds. It is deny-by-default for filesystem paths, leaves outbound internet on by default, and supports host rules via a local proxy and credential masking. `--cloud` instead runs the whole session in a GitHub-hosted ephemeral Linux sandbox.

## Key points
- Runs: local process by default. `--cloud` runs the session in a GitHub-hosted isolated, ephemeral Linux "cloud sandbox", billed by usage (https://docs.github.com/en/copilot/concepts/copilot-surfaces/copilot-cli). The same local sandbox also exists in the GitHub Copilot app.
- Isolation: OFF by default. "Until you enable it, the shell commands ... execute directly on your machine with the same access as your user account." MXC (https://github.com/microsoft/mxc, "Policy-driven, layered isolation and containment") picks the backend. macOS uses Seatbelt with a process-scoped profile per command (tested on macOS 15+). Linux uses bubblewrap >= 0.5.0, plus `unshare`/`nsenter` (util-linux >= 2.35) when outbound traffic is allowed. Windows needs a recent Windows 11 build (September 2026 update recommended); feature support varies by build, and unsupported features are reported rather than silently weakened. Docs place it at "the lighter-weight end" of the spectrum, with no VM or container. The sandbox covers shell commands, the ripgrep-based `grep`/`glob` tools, and, by default, local MCP and LSP servers.
- Filesystem (sandbox): deny-by-default with read/write, read-only and denied levels. Read/write covers the cwd and temp. In a Git repo the whole repo is readable, while writes are limited to cwd plus `.git`. PATH and toolchain dirs are read-only ("Allow dev tool access"), some package caches are writable, and the home directory is not granted. Built-in file read/edit tools run in-process, so the same policy is only a software check for them. `/sandbox policy [cmd]` shows the effective policy.
- Filesystem (no sandbox, tool-level): default path permission covers the cwd, its subdirectories and system temp. For shell commands, paths are "heuristically extracted by tokenizing command text", and the docs list limitations (complex constructs, unexpanded custom variables, symlinks for new files). Flags: `--allow-all-paths`, `--disallow-temp-dir`, `/add-dir`. Trusted folders are stored in `~/.copilot/config.json` (`trustedFolders`), and the docs say scoping "is heuristic" with no guarantee for files outside them (https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/configure-copilot-cli).
- Network: without the sandbox, `web_fetch` and a curated list of shell commands (`curl`, `wget`...) need URL approval. URLs are found with regex, and `--allow-url`/`--deny-url`/`--allow-all-urls` and `allowedUrls` adjust this. With the sandbox, outbound internet is ON by default and local network OFF, and host allow/deny rules go through a built-in local proxy. On macOS and Linux the OS restricts connections to that proxy. On Windows it relies on programs honouring proxy settings, which is weaker. On Linux bubblewrap cannot separately control local-network access for spawned processes. Credential masking gives sandboxed tools placeholder Git/`gh`/env tokens, and the proxy injects the real ones only for approved HTTPS hosts (https://docs.github.com/en/copilot/how-tos/cloud-and-local-sandboxes/using-local-sandboxing).
- Approvals: read-only operations are auto-allowed, while writes, destructive shell commands and URLs prompt (once or for the session, or saved per repo in `~/.copilot/permissions-config.json`). Rules use `--allow-tool` and `--deny-tool` (e.g. `shell(git:*)`, `write(path)`, `MyMCP(tool)`), and deny beats allow even under allow-all. `--available-tools` and `--excluded-tools` hide tools from the model. YOLO: `--allow-all-tools`, `--allow-all` = `--yolo` (tools+paths+urls), or `/yolo`, `/permissions allow-all` in session. LLM-judged "assisted permissions" come via `/permissions assisted`, `defaultPermissionMode: "assisted"` or `--assisted-approval`. Sandbox bypass requests are on by default, and an approved bypass also skips credential masking and the proxy (https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/allowing-tools).
- Enterprise: `permissions.disableBypassPermissionsMode: "disable"` blocks the allow-all family. Managed settings (server-managed, MDM, file-based) compose in the most-restrictive direction. They can require sandboxing (`sandbox.enabled`), add denied paths, lock "Include working directory", and with `sandbox.failIfUnavailable: true` block model requests and tools if the sandbox cannot be enforced. If policy permits bypass, users can still opt out for one session (`/sandbox disable`).
- History: the sandbox appears in the CLI changelog by 1.0.57 (2026-06-01). 1.0.62 (2026-06-13) mentions `mxc-sdk`, and a shell-command bypass option was added in the same period (github/copilot-cli changelog.md).

## Relevance to the talk
This is the clearest current example of the layered model. One layer is heuristic tool-level path and URL checks, which GitHub itself says are not guaranteed. The next is an opt-in OS sandbox (Seatbelt/bubblewrap/Windows-native via Microsoft's MXC) with deny-by-default filesystem rules, open internet by default, a credential-injecting proxy, and admin "fail if unavailable". The last is a full cloud VM a flag away. It also shows that Windows native sandboxing finally arrived in 2026, but with proxy-honouring caveats.
