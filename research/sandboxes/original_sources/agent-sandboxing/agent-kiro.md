## Summary
Kiro (AWS) ships an IDE, a CLI and a Web/Mobile cloud agent. The IDE and CLI run the agent harness as a local process on your machine. Since Kiro IDE 1.3 and CLI 2.31 they can wrap the agent's shell commands (and, optionally, stdio MCP servers) in an OS sandbox: Seatbelt (`sandbox-exec`) on macOS, bubblewrap on Linux, and a native mechanism on Windows that needs a one-time admin setup. The sandbox is **off by default**. It is forced on, with network blocked, when the CLI enters `/autonomous on` mode, and organizations can require it. Without it, commands run as the user, gated by a capability-based `permissions.yaml` rule engine (deny > ask > allow > evaluate). Kiro Web and cloud sessions run in an Amazon-managed cloud sandbox that approves every action by default. **Amazon Q Developer CLI is folded into this note:** AWS says "The Q CLI has become the Kiro CLI", and Q CLI users were auto-updated to Kiro CLI on 2025-11-24.

## Key points
- Product status: current. Kiro CLI is the successor to Amazon Q Developer CLI. AWS's Q docs now say "The Q CLI has become the Kiro CLI" (https://docs.aws.amazon.com/amazonq/latest/qdeveloper-ug/command-line.html, read 2026-11-22). Kiro's upgrade guide says Kiro CLI shipped 2025-11-17 and Q CLI with auto-update on became Kiro CLI on 2025-11-24. Kiro CLI keeps the `q` / `q chat` entry points and the Q config, and is closed source (AWS IP License), where Q CLI was Apache-2.0 (https://kiro.dev/docs/upgrade-guides/migrating-from-q/). The open-source `aws/amazon-q-developer-cli` README says the project "is no longer being actively maintained and will only receive critical security fixes" (repo not archived; last push 2026-08-24).
- Runs: the IDE and CLI run the harness locally, so shell commands run in your shell with your credentials. Web and Mobile run the same harness in a managed cloud sandbox, and the IDE/CLI can also attach to these "cloud sessions" (https://kiro.dev/docs/how-kiro-works/).
- Isolation (local, opt-in): macOS uses Seatbelt via `sandbox-exec`. Linux uses `bwrap` on PATH, which Kiro does not install, plus `socat` for the filtering modes. Windows uses a one-time administrator setup (`/sandbox setup` in the CLI); the mechanism is not named, and `DEFAULT_BLOCKED` works before setup. The harness and the built-in file tools stay **outside** the sandbox; only shell commands, their children and (with `mcpSandboxing: true`) stdio MCP servers are inside. If the backend is missing, commands "run without operating-system isolation" unless an organization requires the sandbox, in which case they are refused.
- Turning it on: `sandbox.json` with `"enabled": true`, either global (`~/.kiro/settings/sandbox.json`) or per project (`.kiro/settings/sandbox.json`). In the CLI, `/sandbox on|off|project on|network|setup`. A project file can only tighten an active global policy, so a cloned repo cannot open the network or switch the sandbox off. For headless runs, `kiro-cli chat --v3 --sandbox --no-interactive ...` fails closed if the sandbox cannot activate.
- Autonomous mode: in the CLI, `/autonomous on` switches to the Default agent and forces the sandbox on with outbound network blocked. If protection cannot be confirmed, autonomous mode does not start, and if protection is lost it exits. Kiro Web "Autonomous mode" is a separate cloud feature (https://kiro.dev/docs/web/autonomous-mode/).
- Filesystem: with no `permissions.yaml`, the defaults allow silent `fs_read` of `./**`, git read-only commands and system-info commands, and everything else prompts. Hard-coded denies cover writes to `~/.kiro/settings/`, `.kiro/settings/`, `~/.kiro/workspace-roots/`, `.kiroignore` and Kiro state stores. Writes to `.git/**`, `.vscode/**`, and the `.kiro` `agents`, `hooks`, `workflows` and `powers` directories always ask. These are tool-level checks. Inside the sandbox, `fs_read`/`fs_write` rules also shape which paths commands can see and write at the OS level. `.kiroignore` is tool-level and blocks reads and search results (https://kiro.dev/docs/kiroignore/).
- Network (local sandbox): `networkAccess` is `DEFAULT_BLOCKED` (the default), `COMMON_DEPENDENCIES` or `DEFAULT_ALLOWED`, refined per host by `sandbox_network` permission rules. The `all` meta-capability and the `allow-all` preset deliberately exclude `sandbox_network`. Without the sandbox, there is no network control on shell commands.
- Approvals: the `permissions.yaml` capabilities are `fs_read`, `fs_write`, `shell`, `web_fetch`, `web_search`, `mcp`, `subagent`, `skill`, `power`, `context`, `diagnostics` and `sandbox_network`, with effects `deny`/`ask`/`allow`/`evaluate`. They apply at Kiro, administration (`managed-settings.json`), user, workspace (stored outside the repo in `~/.kiro/workspace-roots/<hash>/`), agent and session scope, and the most restrictive effect wins. Compound shell commands are split and each part is checked, and commands too complex to parse are blocked in V3. Headless runs treat `ask` as deny.
- YOLO paths: the CLI has `--trust-all-tools` and `/tools trust-all` (with a confirmation warning), plus the `allow-all` preset (`capability: all, effect: allow`). Kiro's docs recommend these for CI or disposable containers. "Approve for me" (IDE, CLI 2.36+, Web) adds a model-based trust classifier (`evaluate` effect) for actions no rule settles. Workspace trust (CLI 2.33+, `--trust-workspace` in 2.34+) stops an untrusted repo's agents, steering, MCP config, skills and workflows from loading, and forces a prompt for every shell command.
- IDE modes: the IDE has Autopilot (the default) and Supervised; newer builds add "Accept file changes" and "Approve for me". Kiro states "Supervised mode is a code review workflow, not a security control" (https://kiro.dev/docs/privacy-and-security/). The pre-1.0 IDE settings `kiroAgent.trustedCommands` (string-prefix match that "does not analyze command structure, chains, or special characters") and the Command Denylist were replaced by `permissions.yaml` shell rules (https://kiro.dev/docs/ide/0x-reference/).
- Cloud (Web/cloud sessions): each task runs in an isolated sandbox that clones the repo server-side. The isolation technology is not documented. Kiro Web does not use `permissions.yaml` and "approves every action by default" inside the sandbox. Internet access has three levels — "Connections access only" (git hosting only), "Common dependencies" (a long registry allowlist) or "Open internet" — plus a custom domain allowlist (https://kiro.dev/docs/web/sandbox/internet-access/). Which level is the default is not stated. Admins can attach cloud sessions to a VPC.
- Legacy Q CLI (before Kiro): `q chat --trust-all-tools` and `/tools trust <tool>` were the per-tool trust switches. The nx "s1ngularity" malware used `q chat --trust-all-tools --no-interactive` (see nx-s1ngularity-ai-cli-malware.md). The old AWS page `command-line-chat-security.html` now redirects away, so the Q-era wording is not citable from AWS directly.

## Relevance to the talk
Kiro is an example of tying autonomy to isolation: the "let it run" switch (`/autonomous on`) refuses to start unless the OS sandbox is up with the network closed. It uses the now-standard Seatbelt/bubblewrap pair. It also shows the lineage: Q CLI's blunt `--trust-all-tools`, which the s1ngularity malware borrowed, survives in Kiro CLI next to a much richer rule engine. The project-file-can-only-tighten rule is a direct answer to repo-supplied config attacks.
