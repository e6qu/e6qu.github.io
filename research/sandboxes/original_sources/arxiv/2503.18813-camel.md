## Summary
CaMeL (Google/DeepMind/ETH) wraps the LLM in a protective system layer instead of trying to make it immune. A privileged LLM turns the trusted user query into a program (control and data flow fixed up front); untrusted data is only ever handled by a quarantined LLM with no tool access, so it can never change what the program does. Values carry capabilities (provenance and allowed readers), and policies are checked when tools are called, blocking exfiltration over unauthorised flows. On AgentDojo it solves 77% of tasks with provable security vs 84% undefended.

## Key points
- Control/data flow extracted from the trusted query; untrusted data "can never impact the program flow".
- Dual-LLM structure (privileged planner + quarantined parser) executed by a custom interpreter.
- Capabilities attached to data enforce security policies at tool-call time.
- Utility cost: 77% vs 84% tasks solved on AgentDojo.
- Code: github.com/google-research/camel-prompt-injection.

## Excerpts
> "CaMeL explicitly extracts the control and data flows from the (trusted) query; therefore, the untrusted data retrieved by the LLM can never impact the program flow." (Abstract)

> "We demonstrate effectiveness of CaMeL by solving $77\%$ of tasks with provable security (compared to $84\%$ with an undefended system) in AgentDojo." (Abstract)

## Relevance to the talk
The flagship "security by construction" agent design; it is capability-based security (a 1960s-70s idea) reapplied to LLM dataflow. Good for contrasting *semantic* isolation with the OS-level sandboxes most coding agents actually ship.
