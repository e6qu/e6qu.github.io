## Summary
Assumes the coding agent is already compromised and asks what must contain it. Many real exploits share one root cause: a check approves a *name* (path, argv, directory) and a later step maps it to a different *object* (a symlink target, an option's behaviour, a repository git discovers itself), a classic TOCTOU/confused-deputy pattern. Zero-Trust Agent Cells run the agent in a kernel sandbox whose only route out is a socket to a broker that resolves, authorises and re-checks the actual object at use time.

## Key points
- Agent runs in a kernel sandbox; all file, program and network access goes through a broker.
- Approvals bound to the resolved object and single-use; spawned programs run in a sandbox compiled from the same policy.
- macOS prototype, 3.2k lines of trusted Rust.
- 74 attacks with ground-truth oracles incl. 10 replayed public incidents: tool allowlist loses 66; allowlist + command sandbox of the kind deployed agents use loses 56; ZTAC loses 2 (both encode secrets into traffic to an allowed endpoint).
- Benign: 43/46 operations, 8 approval prompts; 4 ms median brokered no-op latency.

## Relevance to the talk
Connects agent sandboxing to Janus/systrace-era lessons (syscall-interposition races) and to brokered designs (Chromium, Capsicum). Its residual failures, exfiltration via allowed endpoints, show that network allowlists leak.
