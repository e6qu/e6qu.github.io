## Summary
A cross-industry catalogue of agent architectures with provable resistance to prompt injection, with ten worked case studies including a software-engineering agent. The unifying rule: once an agent has read untrusted input, it must be structurally unable to take consequential actions driven by it. The authors are explicit that each pattern trades utility for security and that none fits every case.

## Key points
- Six patterns: Action-Selector, Plan-Then-Execute, LLM Map-Reduce, Dual LLM, Code-Then-Execute (CaMeL-like), Context-Minimization.
- Ten case studies, among them an OS assistant, SQL agent, email/calendar assistant and a software engineering agent.
- Recommends combining patterns; no universal solution.

## Excerpts
> "it must be constrained so that it is impossible for that input to trigger any consequential actions" (Section 3)

> "no single pattern is likely to suffice across all threat models or use cases" (Section 5)

## Relevance to the talk
Gives the talk a vocabulary for *architectural* agent sandboxing, which complements OS sandboxing. The software-engineering case study is the honest admission that general coding agents are the hardest case for these patterns.
