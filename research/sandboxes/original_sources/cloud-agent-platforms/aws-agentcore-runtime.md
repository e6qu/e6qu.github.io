## Summary
AgentCore Runtime is AWS's hosted runtime for agent code and MCP/A2A servers. Its documented unit of isolation is **one microVM per session**: each `runtimeSessionId` gets a dedicated microVM with its own CPU, memory and filesystem. The microVM is destroyed and its memory sanitised when the session stops. The docs never name the VMM. They do call the credential endpoint the "MicroVM Metadata Service (MMDS)", which is Firecracker's name for it. AWS's Marc Brooker also said on HN that Runtime is "the same underlying technology as the Lambda MicroVMs" (see `../hackernews/virtualization-density/hn-48642510-lambda-microvms.md`), and Lambda MicroVMs are documented as Firecracker (`aws-lambda-microvms.md`). A second compute type, **Instances**, runs agents on EC2 managed instances in the customer's account. There, the session maps 1:1 to an EC2 instance, and the docs say plainly that agents sharing an instance are *not* isolated from each other.

## Key points
- **Unit and scope (microVMs):** "Each session in AgentCore Runtime receives its own dedicated microVM with isolated compute, memory, and filesystem resources." One sandbox per *session*, not per tenant or per agent. The client chooses the session ID, which must be at least 33 characters. The session header routes requests to the same microVM ("microVM stickiness").
- **Lifecycle:** Sessions are Active, Idle or Stopped. The idle timeout defaults to 15 min (`idleRuntimeSessionTimeout`) and the maximum lifetime defaults to 8 h (`maxLifetime`), and both are configurable up to 8 h on microVMs. After a stop, the same session ID gets a *new* microVM. Synchronous requests time out at 15 min, and async jobs can run up to 8 h on microVMs and up to 14 days on Instances.
- **Teardown:** "After session completion, the entire microVM is terminated and memory is sanitized to remove all session data."
- **Snapshots (platform V2):** V2 "starts your agent from a snapshot": it prepares the environment once, snapshots it at the first healthy `/ping`, and restores that snapshot for every new session. The consequence is that anything created at import time (for example an AWS SDK client) carries pre-session credentials into every session. The docs tell you to create clients inside the handler. V2 also allows 10 GB images (V1: 2 GB).
- **Persistence:** The microVM is ephemeral by default. Optional "session storage" is a persistent directory (≤1 GB per session) that survives stop/resume. EFS and S3 Files mounts are also supported. "Permissions are stored but not enforced within the session … because the agent runs as the only user in the microVM."
- **Session pinning (V2 only):** A session created with a user identity (JWT `sub` + `iss`, or a SigV4 `X-Amzn-Bedrock-AgentCore-Runtime-User-Id` header) is pinned to that user, and other users get `AccessDeniedException`. On V1 and Instances, "AgentCore does not enforce session-to-user mappings". A guessed or reused session ID can therefore route one user into another's session if the backend doesn't bind them.
- **Credentials:** Each session gets the runtime's IAM execution role via MMDS. "Any code or actor running inside the microVM can access execution role credentials by calling the metadata endpoint (MMDS)." MMDSv2 (session-token) is mandatory from 2026-06-30. V2 adds IAM context keys `aws:AgentCoreRuntimeSourceSid` / `aws:AgentCoreRuntimeSourceArn` to scope one role per session (for example, an S3 prefix per session), but they "do not prove that a request was made from inside the corresponding microVM." Third-party OAuth/API-key access goes through AgentCore Identity (see `aws-agentcore-gateway-identity-policy.md`).
- **Shell access into the sandbox:** `InvokeAgentRuntimeCommand` (one-shot, 1–3600 s) and `InvokeAgentRuntimeCommandShell` (interactive PTY over WSS, ≤1 h) run in the same microVM as the agent: "The isolation boundary is the microVM itself."
- **In-VM platform server:** Each microVM runs a localhost "platform server" for lifecycle, storage and shell. The docs tell you to stop agent tools from reaching localhost, because doing so "can disrupt the session's VM lifecycle or provide shell access within that session".
- **Network:** `networkMode` is `PUBLIC` (open internet egress; the examples use it) or `VPC`. In VPC mode, ENIs are created in customer subnets, egress is governed by security groups, and there is no internet without a NAT gateway ("Using a public subnet does not provide internet connectivity"). Runtime has no built-in domain allowlist. The Gateway in front and VPC controls (Route 53 DNS Firewall etc.) are the documented levers. IAM condition keys `bedrock-agentcore:subnets` / `securityGroups` can force VPC deployment.
- **Limits:** The default is 2 vCPU / 8 GB per session. V2 resource configurations offer a baseline of 0.25–2 vCPU, bursting to 4× (peak 8 vCPU / 32 GB, disk 10–32 GB). There are 5,000 active sessions per account in us-east-1 and us-west-2 (2,500 elsewhere), and new sessions are created at 25 TPS.
- **Instances compute type:** Instances are EC2 managed instances in the customer's account and VPC. "Agents on an instance are not isolated from each other … neither provides a security boundary between workloads on the same instance." "The session is the isolation unit": one session maps to one instance. `STANDARD` mode runs a container in a user namespace with seccomp and masked `/proc`/`/sys`. `PRIVILEGED` mode is equivalent to `docker run --privileged`, and such a session hosts only one agent. Credentials are not isolated between agents on one instance.
- **Pricing (aws.amazon.com/bedrock/agentcore/pricing):** Billing is per second for vCPU-hours and GB-hours. V1 costs $0.0895/vCPU-h and $0.00945/GB-h. V2 consumption pricing is $0.1276/vCPU-h and $0.0169/GB-h, and the committed baseline is $0.0997/vCPU-h and $0.0132/GB-h. "CPU scales to zero during I/O wait (waiting for LLM responses, tool / API calls, or database queries)." V2 reclaims idle memory after 120 s.
- **Regions:** V2 is in 19 Regions (US, Canada, 7 EU, 8 APAC, São Paulo). VPC mode lists 22 Regions including GovCloud (US-West).

## Relevance to the talk
This is the hyperscaler reference design for hosted agents: a microVM per session, snapshot-restored, torn down with memory scrubbing, and billed for CPU only while not waiting on the LLM. It also shows the seams that remain inside a good VM boundary: the IAM role is reachable from any code in the VM, session IDs act as bearer-ish routing keys unless pinned, an in-VM control server sits on localhost, and snapshot restore leaks pre-session state into every session. The Instances option is an unusually honest counterpoint: the moment agents share an EC2 box, AWS's own docs say there is no boundary between them.
