## Summary
Pillar Security showed that AI "rules" files (`.cursor/rules`, Copilot instruction files), which developers share and fork as ordinary project config, can carry instructions hidden with invisible Unicode characters such as zero-width joiners and bidi markers. The model reads them and a human reviewer does not. In the demo the poisoned rule made the assistant add an attacker `<script>` tag to generated HTML and tell it not to mention the change. Because rules files live in the repo, the backdoor persists across sessions and spreads through forks and templates. Pillar calls the technique "Rules File Backdoor".

## Key points
- Vector: shared configuration that the agent treats as trusted, high-priority instructions, a poisoned repo artefact rather than a poisoned package.
- Pillar says the hidden characters also stay invisible in GitHub pull-request review.
- Vendor responses (Pillar's timeline): Cursor (reported 2025-02-26) concluded on 2025-03-06 that the risk "falls under users' responsibility", and kept that position on 2025-03-08. GitHub (reported 2025-03-12) replied that users are responsible for reviewing and accepting Copilot's suggestions, and on 2025-05-01 added a warning for hidden Unicode text on github.com.
- What it compromises is the *code the agent writes*, which ends up in the product, rather than the developer's machine.

## Excerpts
> "users are responsible for reviewing and accepting suggestions generated by GitHub Copilot." (GitHub's reply, quoted in Pillar's timeline)

> "we must now consider the AI itself as part of the attack surface that requires protection." (Conclusion)

## Would a mature sandbox have stopped it?
**No.** This is the case that marks the limit of sandboxing. The agent did exactly what it is allowed to do, writing code into the workspace, and the harm happens later, in production or in a user's browser. Filesystem scope, egress allowlists and credential isolation are all beside the point. What helps is provenance and integrity for instruction files: flagging or stripping invisible and bidi Unicode in rules files, which GitHub's 2025-05 warning partly does; treating repo-supplied rules as untrusted input; and code review or SAST on agent output. A sandbox would only matter if the injected rule told the agent to *do* something (run a command, fetch a URL). Then the usual controls apply: no write access to agent config and a default-deny egress allowlist.

## Relevance to the talk
A counterpoint slide: "sandbox the agent" does not cover an agent that is turned into a code-supply-chain injector. It also previews a pattern seen later with CurXecute, Copilot's settings.json, Claude Code hooks and Mini Shai-Hulud: files that configure the agent are executable in effect and need protecting like code.
