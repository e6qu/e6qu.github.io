## Summary
Microsoft Execution Containers (MXC) 1.0: a cross-platform SDK that applies a policy ("what may this workload
touch?") using the OS's own process sandbox: AppContainer-based process containers on Windows, bubblewrap on
Linux, Seatbelt on macOS; a commenter also mentions a hyperlight (micro-VM) backend, not checked here. A second thread on the Windows blog post
the same day: "Mxc: Microsoft Execution Containers version 1.0.0" (228 points,
https://news.ycombinator.com/item?id=50016956).

## Key points
- Seen as a frontend that makes bubblewrap/Seatbelt/process containers consistent; praised for "learning",
  audit and debug modes that discover what a runtime needs.
- Criticism: on macOS it shares the host kernel (Seatbelt only), "not nearly the same as microvm"; an
  abstraction spanning bubblewrap and hyperlight looks awkward; large, possibly LLM-written codebase.
- From the second thread: Windows 11 25H2 (August update) lets non-admins create AppContainers, which MXC builds on.
- Context: "everyone is building the same sandbox"; UWP's earlier capability model was rejected by developers.
- One commenter claims a sandbox escape and wrong capability ordering, without evidence; asked for proof.

## Relevance to the talk
The industry's cross-platform "lighter option" is OS-native process sandboxing, with Seatbelt as the macOS leg;
the HN critique (shared kernel) is exactly the trade-off the talk weighs against VM-per-agent.
