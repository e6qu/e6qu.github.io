## Summary
SandboxFusion is ByteDance Seed's HTTP service for running and grading LLM-generated code. It is used for evals such as FullStack Bench, HumanEval, MBPP and LiveCodeBench, and for RL. It supports about 20 languages plus Jupyter and CUDA. Its isolation is lightweight and hand-built rather than VM- or container-based. In `lite` mode each run gets an overlayfs over the host root (tmpfs upper layer), a chroot, a cgroup (4 GB memory, 1 CPU), a PID namespace and a network namespace. The code says this adds "< 100 ms" overhead. The default local config turns isolation off.

## Key points
- Isolation unit: a per-run process with "handcrafted overlayfs + chroot + cgroups isolation". The config literal is `isolation: Literal['none', 'lite']` (sandbox/configs/run_config.py).
  - In `lite`, sandbox/runners/base.py wraps each compile or run command as `cgexec -g … unshare --pid --fork --mount-proc ip netns exec <netns> chroot <overlay_root> bash -c …`.
  - The cgroup is created with `tmp_cgroup(mem_limit='4G', cpu_limit=1)`.
  - The overlay lowerdir is the host `/`, with upper and work dirs on a tmpfs. `/dev` is rbind-mounted, and `/etc/hosts` and `/etc/resolv.conf` are copied in (sandbox/runners/isolation.py).
  - No user namespace or UID drop is used in `lite`. `set_uid` applies only in `none` mode.
  - There is no seccomp, gVisor or VM.
- Per-session?: one isolation context per execution request. There are no persistent sessions, except for the Jupyter runner.
- Network egress: each run gets a fresh network namespace created by a sudo helper script (`create_net_namespace.sh`, subnets from 172.16/12, optional `netns_no_bridge`). Whether the default bridge gives internet access was not verified. The service itself now binds to 127.0.0.1:8080 by default.
- Persistence: none. Writes land in a throwaway tmpfs overlay. Requested output files are read back from the overlay root.
- Limits: 4 GB memory and 1 CPU per run in `lite` (base.py). Run timeouts are set per request. `max_concurrency: 34` in local.yaml, with the comment "overselling is key to reduce cost".
- Defaults: `sandbox/configs/local.yaml` sets `isolation: none`, and `ci.yaml` sets `isolation: lite`. I did not verify which config the published server image uses.
- Languages: the docs list Python (CPU and GPU), C++, C#, Go, Java, Node.js, TypeScript, Lean, Scala, Kotlin, PHP, Rust, Bash, Lua, R, Perl, D, Ruby, Julia, Verilog and CUDA, plus a python3 Jupyter kernel (https://bytedance.github.io/SandboxFusion/docs/docs/get-started).
- Deployment: `docker run -it -p 8080:8080 volcengine/sandbox-fusion:server-20250609`, with a China mirror at `vemlp-cn-beijing.cr.volces.com/preset-images/code-sandbox:server-20250609`. Note the image lives under the `volcengine` Docker Hub org.
- Repo facts at access time: about 1.1k stars, Apache-2.0, no GitHub releases listed.
- Paper: "FullStack Bench: Evaluating LLMs as Full Stack Coders", arXiv:2412.00535, Bytedance-Seed-Foundation-Code-Team. v1 2024-11-30, v6 2025-05-12. The abstract says they "release an effective code sandbox execution tool (i.e., SandboxFusion)". The benchmark covers 16 programming languages.
- Reuse: the AIO Sandbox architecture lists "Sandbox Fusion" as its code-execution component (see bytedance-aio-sandbox.md).

## Relevance to the talk
SandboxFusion shows what "sandbox" often means in LLM training and eval: built for throughput and reproducibility rather than hostile-tenant security. It is DIY Linux primitives (overlayfs, chroot, cgroups v1 tools, netns, PID ns) with no user namespace or seccomp, oversold concurrency, and isolation off by default for local use. It is a useful contrast with the microVM boundary that the same company sells on Volcano Engine for agents.
